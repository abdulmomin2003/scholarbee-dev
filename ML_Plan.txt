── Task 6: Synthetic warm-up data generator ───────────────────
File: src/recommendation/scripts/generate-warmup-impressions.ts

Purpose: Bootstrap the ML model immediately by generating realistic
synthetic impressions from existing behavioral events + onboarding data.
This is NOT fake data — it is derived from real student behavior already
in the database, reformatted as labeled impressions.

Logic:
  1. Load all existing behavioral events (clicks, favorites, applies)
  2. For each event, find the corresponding program
  3. Extract its feature scores against the student's profile
  4. Create an Impression document with:
       label = 1 (the student did engage with this program)
       was_clicked/favorited/applied = true (from event type)
       session_id = 'warmup_' + event._id
       scoring_engine = 'rules'
       features = computed from existing scoring engine
  5. For each positive impression, generate 3–5 negative impressions
     (programs the student did NOT engage with, from same field/city pool)
     with label = 0
     This creates a realistic 1:4 positive:negative ratio

Run as: npx ts-node src/recommendation/scripts/generate-warmup-impressions.ts
Add a guard: skip if labeled_impressions already > 100 (don't double-generate)
Log: how many positive and negative impressions were created

── Task 5: training/dataset.py ────────────────────────────────

Class DatasetLoader:

  async def load(db, config) -> DatasetResult:

    1. Query MongoDB impressions collection:
         { label: { $in: [0, 1] } }
       Project: features, label, student_id, program_id, shown_at

    2. Build feature matrix via FeatureExtractor

    3. Validation (soft — log warnings, do not raise unless critical):
         - If n_samples < config.MIN_TRAINING_SAMPLES:
             log WARNING with count and threshold
             proceed anyway (bootstrap mode)
         - If positive_rate < config.MIN_POSITIVE_RATE:
             log WARNING
             proceed anyway
         - If n_samples < 50: raise DatasetError (truly too little)

    4. Stratified train/test split (test_size=0.2, stratify=y)
       If n_samples < 100: use test_size=0.1 to preserve training data

    5. Return DatasetResult:
         X_train, X_test, y_train, y_test,
         n_samples, positive_rate, n_students, n_programs,
         feature_columns = FEATURE_COLUMNS,
         bootstrap_mode: bool  (true if n_samples < MIN_TRAINING_SAMPLES)

── Task 6: training/trainer.py ────────────────────────────────

Class ModelTrainer:

  async def train(db, config) -> TrainingResult:

    1. Load dataset via DatasetLoader.load()
       If DatasetError: raise — not enough data even for bootstrap

    2. Select model based on dataset size:

       If n_samples < 500 (bootstrap mode):
         Use LogisticRegression only, no grid search:
           LogisticRegression(C=1.0, max_iter=500,
                              class_weight='balanced',
                              random_state=42, solver='liblinear')
         Wrap in StandardScaler pipeline
         Fit directly on X_train

       If n_samples >= 500:
         GridSearchCV over LogisticRegression:
           param_grid = {
             'classifier__C': [0.01, 0.1, 1.0, 10.0],
             'classifier__penalty': ['l1', 'l2'],
             'classifier__solver': ['liblinear']
           }
           cv=5, scoring='roc_auc', n_jobs=-1

    3. Evaluate via ModelEvaluator.evaluate()

    4. Quality gate:
       Bootstrap mode (n_samples < 500):
         Accept if AUC-ROC >= 0.50 (better than random)
         Log clearly: "Bootstrap model trained — improves as data grows"

       Production mode (n_samples >= 500):
         Accept if AUC-ROC >= 0.60
         Reject below 0.60 — keep old model if one exists

    5. Save model:
         joblib.dump(pipeline, config.MODEL_PATH)
         version = datetime.utcnow().strftime('%Y%m%d_%H%M%S')
         Save metadata JSON:
           version, trained_at, n_samples, positive_rate,
           auc_roc, precision_at_10, bootstrap_mode,
           feature_columns, best_params (if grid search ran)

    6. Reload scorer (hot reload)

    7. Return TrainingResult with all of the above

── Task 7: training/evaluator.py ──────────────────────────────

Class ModelEvaluator:

  def evaluate(model, X_test, y_test) -> EvaluationMetrics:
    Compute:
      auc_roc:           sklearn roc_auc_score
                         If only one class in y_test (small dataset):
                           set auc_roc = 0.5, log warning
      precision_at_10:   among predictions ranked top-10 by probability,
                         fraction that are actually positive
                         If test set has < 10 samples: use all samples
      recall_at_10:      fraction of positives captured in top-10
      feature_importance: dict of feature → abs(coefficient)
                          from pipeline['classifier'].coef_[0]
      class_distribution: { positive: int, negative: int }

    Return EvaluationMetrics dataclass

── Task 1: MLScorerService (NestJS) ───────────────────────────
File: src/recommendation/ml-scorer.service.ts

Config from environment:
  ML_SERVICE_URL:      string  (default: "http://ml-service:8002")
  ML_ENABLED:          boolean (default: false)
  ML_SHADOW_MODE:      boolean (default: true)
  ML_TIMEOUT_MS:       number  (default: 500)
  ML_ROLLOUT_PCT:      number  (default: 0, range 0-100)

Methods:

  async getHealth(): Promise<MLHealthStatus>
    GET {ML_SERVICE_URL}/health
    Returns health payload or { status: 'unreachable' } on error
    Never throws.

  async isReady(): Promise<boolean>
    Calls getHealth(), returns model_loaded boolean
    Returns false on any error.

  async score(
    studentId: string,
    candidates: ScoredProgram[],
    featureSnapshots: Record<string, ProgramFeatures>
  ): Promise<MLScoreResult[] | null>
    - Build /score request payload from candidates + snapshots
    - POST to ML service with ML_TIMEOUT_MS timeout
    - Returns null on: error, timeout, 503 (model not ready)
    - Returns MLScoreResult[] on success
    - Logs warn on failure, never throws

  async scoreInShadow(
    studentId: string,
    rulesRanked: ScoredProgram[],
    featureSnapshots: Record<string, ProgramFeatures>
  ): Promise<void>
    - Calls score()
    - If null: log "ML unavailable, shadow skipped"
    - If scores received:
        a. Build ML-ranked order
        b. Compute Spearman rank correlation (implement in ~10 lines)
        c. Save ShadowComparison to MongoDB (Task 2)
        d. Log: { student_id, correlation, ml_top3, rules_top3 }
    - Always fire-and-forget — never awaited by caller

  isEligibleForML(studentId: string): boolean
    - Hash studentId deterministically to 0-99 bucket
      parseInt(sha256(studentId).slice(0,8), 16) % 100
    - Return bucket < ML_ROLLOUT_PCT
    - Same student always gets same bucket (not random per request)

  async getRanked(
    studentId: string,
    rulesRanked: ScoredProgram[],
    featureSnapshots: Record<string, ProgramFeatures>
  ): Promise<{ ranked: ScoredProgram[], engine: 'rules' | 'ml' }>
    - If ML_ENABLED=false OR ML_SHADOW_MODE=true:
        fire scoreInShadow() without await
        return { ranked: rulesRanked, engine: 'rules' }
    - If ML_ENABLED=true AND ML_SHADOW_MODE=false:
        if NOT isEligibleForML(studentId):
          return { ranked: rulesRanked, engine: 'rules' }
        mlScores = await score(...)
        if mlScores is null:
          return { ranked: rulesRanked, engine: 'rules' }  ← fallback
        sort candidates by ml_score
        apply partner/freshness boosts as tiebreakers
        return { ranked: mlRanked, engine: 'ml' }

  Root Cause Analysis — Interacted Programs Not Rising to Top
There are three distinct bugs — each affecting a different ranking mode:

Bug 1: behavioralScore has a constant +0.30 floor for everyone (breaks behavioral & hybrid mode)
typescript
// Line 392 — Search Query Align
behavioralScore += w.SEARCH_QUERY_ALIGN * 1.0;  // +0.15 for ALL programs
// Line 410 — Dwell Time
behavioralScore += w.DWELL_TIME * 1.0;           // +0.15 for ALL programs
SEARCH_QUERY_ALIGN and DWELL_TIME are not tracked — they always get a score of 1.0 for every single program. This means every program starts with a +0.30 behavioral floor, before any real signals are applied.

The clicked program gets: 0.30 (floor) + 0.20 (click) = 0.50 An un-clicked program gets: 0.30 (floor) + 0.00 = 0.30

The gap is only 0.20 across a 1.0 range — but since APPLICATIONS also adds 0.30 if applied, programs you've applied to score 0.60 even with zero clicks. The click signal is diluted by the constant noise floor.
